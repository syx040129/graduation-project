# 一 选题背景与研究意义

## 1.1 选题背景

网络招聘将岗位发布、简历投递和候选人筛选迁移到线上，为求职者与企业提供了便捷的信息交流渠道。不过，岗位数量增加并不意味着求职者能够迅速找到适合自己的岗位。职位描述与简历通常采用自然语言表达，同一项技能可能存在不同写法，岗位要求也包含经验、学历与项目能力等多个维度。只按岗位名称或关键词检索，难以解释候选人与岗位之间的具体差距；仅凭综合分排序，又容易使求职者和招聘人员无法判断评分依据。

招聘网站还涉及完整的业务协作过程。求职者需要管理多份简历、了解投递进展并获得有针对性的改进建议；企业需要维护岗位、处理投递并查看候选人材料；管理员需要管理账号、岗位和举报信息。若这些功能之间缺少一致的权限与状态约束，可能出现跨企业读取简历、重复投递、岗位下架后仍被推荐等问题。因此，本课题拟将招聘业务流程、可解释的岗位匹配与数据访问控制结合起来，设计并实现“智聘通”招聘网站。

本课题以现有 CareerNova 项目为工程基础。项目采用 Spring Boot 与 Vue 的前后端分离结构，已有三角色门户及多项招聘辅助功能。开题研究将在核对现有功能的基础上，进一步完成需求分析、设计论证、关键机制完善和实验评价。文中的“智聘通”为本课题统一使用的系统名称，代码和部分项目材料中的“CareerNova”“智聘 AI”指向同一工程基础。

## 1.2 研究意义

在应用层面，网站拟将岗位浏览、简历管理、投递处理和结果反馈组织为连续流程，减少求职者在多个页面之间反复查询的操作。岗位匹配结果同时展示技能命中项、缺失项及各维度评分，使求职者能够据此检查简历并准备面试，也为企业提供候选人初步筛选的辅助信息。

在工程层面，本课题能够综合运用软件工程、数据库设计、Web 开发和软件测试知识。研究重点包括多角色权限与资源归属校验、投递状态管理、简历文件访问、推荐缓存更新，以及外部模型不可用时的规则回退。通过源码、数据库约束和测试记录相互核对，形成可演示、可解释、可复核的毕业设计成果。

在方法层面，本课题拟比较规则匹配与语义匹配的组合方式，分析权重、候选集范围和数据变化对推荐结果的影响。匹配分用于辅助理解岗位适配情况，不将其直接解释为录用概率，也不以系统评分替代企业的最终招聘判断。

# 二 国内外研究现状

## 2.1 国内研究现状

国内推荐系统研究已经形成协同过滤、知识驱动及混合推荐等多种技术路线。赵俊逸等对协同过滤推荐系统进行了综述，为比较不同推荐方式提供了基础资料[1]。阳德青等整理了知识驱动推荐系统的研究现状与发展方向[2]。这些研究有助于本课题理解用户画像与岗位画像的建模方式，并根据数据条件选择适合毕业设计的实现路线。

在就业推荐领域，南国芳、陈炫廷围绕“学者—高校”匹配研究双向就业推荐系统，将供需双方的匹配问题纳入系统设计[3]。该场景与一般企业招聘有所不同，但提示本课题应同时考虑求职者的岗位选择与企业的候选人筛选。本系统拟在求职者端提供岗位推荐，在企业端提供已投递候选人的匹配分析；现有工程尚不能据此称为完整的双向推荐算法。

推荐效果的评估同样需要明确实验条件。施韶韵等讨论了数据处理、候选集范围及评价方式等实验细节对推荐结论的影响[4]。因此，本课题拟固定对比方法使用的数据集与候选岗位集合，区分参数调整数据与最终评价数据，避免仅展示个别高分案例便断言推荐效果提升。

## 2.2 国外研究现状

Qin 等提出能力感知的人岗匹配神经网络，将岗位要求与求职经历的文本表示结合，并通过注意力机制分析不同能力要求与经历信息的贡献[5]。这一工作表明，人岗匹配需要处理比关键词重合更复杂的语义关系。本课题将借鉴其按能力维度解释匹配结果的思路，但不计划复现或训练同等规模的神经网络模型。

De Ruijt 与 Bhulai 对岗位推荐系统文献进行综述，关注招聘推荐的时效性、双向性、数据可获得性及公平性问题[6]。对本课题而言，岗位上下架、简历修改和推荐缓存有效期都可能影响结果是否仍然适用；实验数据的来源与规模也会限制评价结论能够推广到何种场景。

## 2.3 现有研究对本课题的启示

已有研究为画像构建、文本匹配和评价方法提供了参考，但本课题现有工程主要使用演示数据，缺少大规模真实投递反馈。直接训练依赖大量历史行为的模型并不符合当前数据条件。因此，拟采用“结构化规则评分＋文本向量相似度”的组合方法，以可复现的规则模式作为基线，保留真实向量模型和语言模型的接入能力。

本课题的研究重点落在可解释匹配与招聘流程的工程实现上：评分结果需要能追溯到输入简历和岗位要求，推荐结果应随业务数据变化而更新，模型异常时应展示实际执行来源。最终将结合功能测试、权限测试与小规模离线评价说明系统的有效性和适用边界。

# 三 研究目标与主要内容

## 3.1 研究目标

本课题拟实现面向求职者、企业和管理员的招聘网站，形成“企业发布岗位—求职者浏览与匹配—提交简历—企业处理—求职者查看反馈”的业务流程。系统应具备清晰的页面导航、稳定的数据持久化和服务端权限控制，并在此基础上提供简历分析、岗位推荐、简历优化、模拟面试及招聘助手等辅助功能。

拟解决的具体问题包括：如何在角色权限之外校验简历与岗位的资源归属；如何使岗位匹配结果兼顾分维度解释与文本相似性；如何避免简历修改和岗位下架后继续展示失效推荐；如何在外部模型失败时保持招聘主流程可用；如何以统一数据和明确指标评价所实现的功能。

## 3.2 功能研究内容

求职者端拟支持注册登录、个人信息维护、岗位检索与详情查看、岗位收藏、多份简历管理、附件上传解析、简历投递及进度查询。简历解析应先形成可确认的预览，再由用户核对后保存，避免直接覆盖原有信息。智能功能围绕具体简历和目标岗位展开，提供匹配分析、岗位推荐、优化建议和模拟面试记录。

企业端拟支持企业档案维护、岗位发布与修改、岗位上下架、岗位技能要求配置、投递列表查看及处理状态更新。企业只能读取投递到本企业岗位的候选人材料，并可通过候选人匹配分析查看技能优势和不足。统计页面展示岗位及投递相关数据，用于了解招聘业务进展。

管理员端拟支持账号管理、企业和岗位管理、简历与投递记录管理、举报处理、操作日志查看及统计展示。管理员可查看人工智能运行模式和执行连通性测试，配置展示应对密钥脱敏。前端页面入口限制与后端接口鉴权共同完成权限控制，不能仅依赖隐藏菜单保护数据。

## 3.3 非功能需求与研究范围

系统拟保证数据完整性、可维护性和可复现性。关键写入流程采用事务，重复投递与重复收藏由业务校验和数据库唯一约束共同限制；文件下载执行授权校验；异常通过统一响应反馈；前后端类型和接口契约保持一致。常用列表采用分页，统计和推荐根据实际场景使用缓存。

本课题以浏览器访问的招聘网站为交付对象，不将支付、视频面试、移动端原生应用或大规模分布式推荐纳入必做范围。真实模型接入作为需单独验证的扩展能力，规则模式应可独立完成演示。模拟面试评分与简历优化属于辅助建议，用户需核对输出是否符合本人经历。

# 四 研究方法与技术路线

## 4.1 研究方法

采用文献研究法，梳理招聘推荐、人岗匹配与推荐实验设计的相关研究；采用需求分析法，从三类用户的操作场景出发，整理功能、权限和状态约束；采用原型与迭代实现法，先确认核心招聘流程，再完善智能辅助与后台治理功能；采用对比实验法和软件测试法，评价匹配方法、异常处理与业务正确性。

技术路线拟按“资料与代码调研—需求分析—总体设计—数据库和接口设计—分模块实现—集成测试—匹配评价—论文整理”推进。每个阶段产生可检查的成果，需求与测试用例相互对应。系统设计与实现分别形成章节，测试报告记录环境、步骤、预期结果和实际结果。

## 4.2 总体架构与技术选型

系统采用 B/S 架构和前后端分离方式。前端以 Vue 3、TypeScript 和 Vite 构建，使用 Vue Router 管理路由、Pinia 管理登录状态，Axios 完成接口调用，Element Plus 提供表单和列表组件，ECharts 展示统计和评分。Vue 的组件化编程模型、Pinia 的共享状态管理及 TypeScript 的类型检查为界面组织和开发校验提供依据[7][8][9]。

后端以 Java 17 和 Spring Boot 3.4.5 为现有技术基础，采用 Controller、Service、Mapper 分层组织。Controller 处理接口输入与角色限制，Service 校验资源归属、状态变化并编排事务，Mapper 通过 MyBatis-Plus 完成持久化。Spring Boot 提供应用配置与服务构建基础[10]。接口采用统一响应和分页结构，文件下载返回经过授权校验的文件流。

数据层采用 MySQL 8，Redis 为可选缓存组件；缓存不可用时现有工程提供内存降级路径。认证采用 Spring Security、JWT 和 BCrypt，后端在请求中检查当前账号状态及角色。人工智能调用通过 Spring AI 封装，向量模型接口用于文本嵌入，业务服务负责模型结果校验与异常回退[11]。核心招聘数据仍以关系数据库为事实来源。

## 4.3 数据库设计

现有 schema.sql 包含 16 张业务表，拟在核对字段与约束后形成数据库设计成果。账号与招聘信息由 sys_user、company、job、job_skill 管理；简历与经历由 resume、resume_experience 管理；投递和收藏由 job_application、favorite 管理；智能辅助结果由 ai_resume_analysis、ai_recommendation、ai_interview、ai_interview_question、ai_chat_session、ai_chat_message 管理；举报和日志由 report、sys_log 管理。

主要逻辑关系包括账号与企业档案的一对一关系、企业与岗位的一对多关系、岗位与技能要求的一对多关系、简历与经历的一对多关系，以及面试场次与题目、对话会话与消息的一对多关系。投递记录关联求职者、岗位和实际所选简历，企业访问权限沿所属岗位进行校验。当前数据库不设置物理外键，关联完整性主要由 Service 校验和事务维护，需重点测试逻辑删除后的关联行为。

数据库设计将明确唯一约束、分页索引、状态取值和逻辑删除规则。简历分析保留每份简历的最新结果；岗位推荐按用户刷新结果；面试报告随面试场次保存。单次岗位匹配与简历优化即时返回，不误写为已独立持久化的结果模块。对于投递唯一键不包含逻辑删除字段所导致的撤销后再投递问题，拟先确定业务要求，再选择与数据库约束一致的处理方式。

# 五 关键技术与拟解决的问题

## 5.1 多维度岗位匹配

现有 JobMatchService 以语义、技能、经验和学历四个维度计算综合分。拟将现有权重作为实验起点：综合匹配分＝0.50×语义分＋0.25×技能分＋0.15×经验分＋0.10×学历分。各维度统一为 0—100 分，最终结果四舍五入并限制在该范围内。上述权重是工程设定，后续通过对比实验分析适用性，不将其视为已证明的最优权重。

技能分由命中岗位技能的权重之和占总权重的比例确定，同时输出命中和缺失技能。学历分按岗位要求与简历学历等级比较。现有经验分主要依据工作、实习及项目经历条数和摘要信息计算，尚不能严格证明候选人具备岗位要求的工作年限，拟将其作为重点核对项，明确评分解释并讨论按经历时间计算年限的改进条件。

语义分由简历文本与岗位描述的向量余弦相似度转换得到。真实模式使用外部向量模型，规则模式采用本地 2-gram 哈希映射的 128 维归一化向量。本地向量更接近字符片段相似度，不能等同于经过训练的语义模型。拟分别记录向量、理由和整体结果的执行来源，确保规则回退结果可辨识。

## 5.2 推荐更新与候选集控制

现有 RecommendationService 先从在线岗位中选择技能命中的候选岗位，无命中时使用备用候选集，再计算匹配分并返回 Top-N。推荐结果支持有效期内复用，并检查简历更新时间。拟验证简历修改、岗位下架和强制刷新后的结果是否一致，分析候选池大小对排序质量与响应时间的影响。

候选池按遍历顺序截断可能遗漏相关岗位，岗位修改也可能使已保存的分值失效。拟在评价时固定候选集，比较全量小规模排序与现有候选池排序；在工程实现中核对失效过滤与重新计算机制。缓存命中不代表评分仍然有效，需将业务变化纳入推荐更新规则。

## 5.3 简历解析与模型输出校验

简历附件拟支持 PDF、DOCX 等项目已有格式，通过 PDFBox、Apache POI 提取文本，再进入解析预览。用户确认后才将内容写入简历。拟重点测试空文件、格式不匹配、文本缺失及上传访问权限等情况，不将扫描版 PDF 的文字识别能力视为现有功能。

真实模型的简历分析、优化、面试和助手回答采用结构化输出，服务端需校验必要字段、类型、分值范围及空值。对网络异常或非法输出执行明确的回退，并记录实际来源。简历优化应保持原始经历事实，生成建议交由用户核对；模型建议不得直接修改已经保存的简历。

## 5.4 权限与业务一致性

权限设计同时考虑角色、资源归属与操作状态。求职者只能修改本人简历；企业只能处理本企业岗位的投递；匿名访客和未获得该投递的企业不能下载简历附件。禁用账号后，旧 Token 也应失效。拟对跨用户、跨企业及管理员接口访问建立正向和反向测试。

投递业务需校验岗位在线状态、简历归属和重复提交，处理状态覆盖待处理、已查看、面试、拒绝和录用等场景，并明确允许的变化规则。岗位下架后应停止新增投递和推荐。对既有投递能否继续处理、撤销后是否允许重新投递等问题，拟形成明确需求，再落实到服务校验与数据约束。

# 六 测试与评价方案

## 6.1 功能与集成测试

拟围绕“发布岗位—创建简历—匹配—投递—企业处理—查看进度”执行集成测试，并覆盖岗位检索、收藏、举报、统计及智能辅助功能。后端使用 JUnit 与 Spring Boot Test 验证关键服务，前端执行类型检查、生产构建和浏览器操作检查。真实数据库集成测试使用独立测试库，避免演示数据与测试写入互相影响。

异常测试包括重复投递、下架岗位投递、非本人简历使用、跨企业访问、禁用账号使用旧 Token、无效附件、模型返回非法 JSON、向量为空或维度异常、缓存不可用等。评价以是否符合既定业务规则为准，不能只统计接口成功响应数量。

## 6.2 匹配效果对比

拟准备不少于 30 份脱敏或合成简历与 50 个岗位描述，组成可复核的小规模评价集；这些数量为计划目标，不是当前已获得数据。按岗位方向与能力层次分组，对候选简历—岗位对进行相关性标注。条件允许时由两名评审独立标注并核对分歧，若只能单人标注则在报告中说明主观性限制。

对比方法拟包括纯技能规则、规则与本地向量组合，以及在可用条件下的规则与真实向量组合。使用相同候选岗位集合，报告 Precision@5、NDCG@5、推荐覆盖率及平均计算时间，并分析技能缺失、文本写法差异和经验要求等失败案例。权重调整使用单独的验证样本，最终评价不反复用于调参。不同模式的结果分别报告，不预先承诺准确率提升幅度。

## 6.3 性能与可用性验证

拟在记录 CPU、内存、数据库规模与网络条件的情况下，测试岗位列表、登录、投递和推荐等接口。以 20 个并发用户为初始负载，记录吞吐量、错误率及响应时间的 P50、P95。普通数据库接口暂以 P95 不超过 2 秒作为本地演示目标；涉及外部模型的接口单独记录延迟、调用失败与回退情况，该目标不等同于生产服务承诺。

拟验证无真实密钥的规则模式启动、数据库连接失败提示、缓存降级、文件授权下载以及服务重启后的报告读取。每项测试保留环境与原始记录，最终结论区分“已通过”“未通过”和“未执行”，确保论文中的描述与实际验证范围一致。

# 七 可行性分析与现有基础

## 7.1 技术与条件可行性

项目已有前后端源码、数据库初始化脚本、功能说明、接口说明和验收文档，可为需求追踪和设计分析提供依据。采用的 Java、Vue 与 MySQL 技术能够支撑本课题范围内的业务；规则模式允许在不依赖外部模型的情况下开展功能演示。现有自动化测试涉及投递、简历、文件访问、岗位匹配、推荐和向量处理等服务，可据此补充针对性回归用例。

本课题主要依赖本地开发环境，软硬件投入可控制在毕业设计可承受范围内。真实模型可能产生调用费用，拟将其作为独立实验条件记录，并在不可用时完成规则模式评价。数据主要使用演示、合成或经授权脱敏的资料，不将未经授权的个人简历用于实验。

## 7.2 现有验证与待完成工作

项目材料记载 2026 年 10 月 8 日曾完成 21 项后端测试、前端类型检查与构建，以及部分本地页面和接口验证。这些记录说明已有一定工程基础，但本开题报告编制时未重新运行上述测试，不能将历史通过结果直接作为本课题最终验收结论。

当前材料同时列出若干待处理事项：空 AI 密钥可能导致自动配置启动失败；在线接口文档存在依赖兼容问题；部分模型超时与输出长度配置尚未落实到调用；撤销投递后的唯一约束语义需要明确；真实模型、Docker 和生产部署尚未完成验收。拟将这些问题按毕业设计交付需要排序，优先保证规则模式运行、核心业务和测试可复现。

## 7.3 数据使用与风险控制

招聘系统涉及简历、联系方式和企业信息，拟在设计中限制访问范围、对实验材料脱敏并避免公开演示真实个人附件。《网络招聘服务管理规定》可作为了解招聘信息管理与服务规范的背景资料[12]。本课题以教学研究和原型验证为范围，正式运营所需条件另行评估。

主要研究风险是标注数据不足、模型不可用和功能范围过大。相应措施为采用透明的小规模评价集、保留规则基线与故障回退、优先完成三角色主流程，并将真实模型评价与部署扩展单独报告。若实验规模不足，论文明确限制结论，不通过扩大表述替代证据。

# 九 预期成果与论文结构

## 9.1 预期成果

预期交付一套可在本地运行和演示的智聘通招聘网站，包含前后端源码、数据库脚本和必要配置说明；形成需求分析、系统设计、数据库设计及接口说明；完成测试报告与岗位匹配对比实验记录；完成毕业设计论文、用户使用说明及答辩演示材料。

验收关注三角色主流程是否连贯、权限边界是否正确、匹配解释是否与实际算法一致、异常回退是否可辨识，以及运行步骤和测试结果是否能够复现。课题特色拟体现为多维度评分的可解释展示、围绕具体简历与岗位的辅助功能，以及规则模式与真实模型模式之间的可核对执行路径，属于工程应用探索，不宣称提出全新的推荐算法。

## 9.2 论文拟定结构

第一章为绪论，介绍背景、意义、研究现状及课题内容。第二章为相关技术，介绍系统使用的开发框架、认证机制和文本匹配方法。第三章为系统分析，明确角色需求、业务流程、权限约束和可行性。第四章为系统设计，阐述总体架构、功能模块、数据库及关键接口设计。

第五章为系统实现，结合关键代码和运行界面说明招聘流程、简历管理、岗位匹配和智能辅助功能。第六章为系统测试与评价，展示功能、安全边界、性能和匹配实验结果，并分析失败案例。第七章为总结与展望，归纳成果和不足，讨论数据规模、评分规则及部署等后续改进方向。
