# 智能招聘网站 —— 人工智能功能说明

> 文档更新：2026-10-08。文件名与引用按当前目录同步；验收记录标注的是历史验证，本轮未重新执行业务测试。 总入口：[项目总文档](项目总文档.md)。

> 范围：AI 的三种运行模式与配置、客户端与服务装配设计、六大 AI 功能（简历分析/岗位匹配/岗位推荐/简历优化/AI 模拟面试/AI 智能助手）的接口与算法、Mock 规则、真实 LLM 接入指引。
> 后端 AI 相关源码集中在 `com.example.recruitment.ai` 包；简历分析、岗位推荐、AI 面试与登录后的 AI 助手对话记录会写入 MySQL；单次匹配不写入推荐批次，简历优化结果仅即时返回，不持久化。

> 运行前提、功能状态和本次实测限制统一见 [项目总文档](项目总文档.md)。示例配置中的模型仅为仓库默认值，供应商当前可用性未联网确认。

## 一、AI 能力总览

| 功能 | 主要端点 | 数据落库 | 真实模式 | Mock 模式 |
| --- | --- | --- | --- | --- |
| 简历分析 | POST/GET /api/ai/resume/analyze、/analysis/{resumeId} | ai_resume_analysis | LLM 结构化 JSON | 确定性规则 |
| 岗位匹配 | POST /api/ai/match | 单次计算不落库 | LLM 推荐理由 + 真实 Embedding 语义，返回实际来源 | 规则 + 本地向量 |
| 岗位推荐 | GET /api/ai/recommendations、POST .../refresh | ai_recommendation | 同上批量计算 | 同上 |
| 简历优化 | POST /api/ai/resume/optimize | 结果即时返回（不落库） | LLM 对照 JD 改写 | 规则化改写 |
| AI 模拟面试 | POST /api/ai/interview/start、/{id}/answer、/{id}/finish、/{id}/report 等 | ai_interview / ai_interview_question / report JSON | LLM 出题/评分/总评 | 内置题库 + 规则评分 |
| AI 智能助手 | GET /api/ai/chat/greeting、POST /api/ai/chat/ask、GET/DELETE /api/ai/chat/history 等 | ai_chat_session / ai_chat_message（未登录不落库） | LLM 多轮问答 + JSON 追问 | 25 个主题规则库 + 数据感知 |

另有企业端“候选人 AI 分析”GET /api/company/candidates/{applicationId}/analysis，服务端复用岗位匹配结果拼接优势/风险/建议。

## 二、运行模式与配置

### 2.1 三种模式判定

AI 模式由三项配置共同决定（AiProperties.displayMode()）：

| 条件 | mode | 说明 |
| --- | --- | --- |
| enabled=true 且 mock=false 且 api-key 非空 | REAL | 调用真实 LLM；Embedding 可由 `embedding-enabled` 控制，关闭时使用本地向量 |
| mock=true | MOCK | 内置规则/题库/本地向量，无需网络与 Key |
| 其余（如 enabled=false 且 mock=false） | DISABLED | 显示状态为 DISABLED，但现有服务多仍走规则分支，不等同于彻底关闭 AI 端点 |

realMode() = enabled && !mock && apiKey 有值。Bean 装配与各服务内部均以该判定选择实现。

### 2.2 Mock 模式配置（默认，开箱即用）

application.yml（默认已生效）：

```yaml
ai:
  enabled: false      # 不启用真实大模型
  mock: true          # 演示/规则模式，无需 API Key
  base-url: "https://api.openai.com" # 通常不手动追加 /v1
  api-key: ""         # 留空即可
  model: gpt-4o-mini
  embedding-model: text-embedding-3-small
  embedding-enabled: true
  temperature: 0.4
  max-tokens: 2000
  timeout-seconds: 30
  recommend-pool-size: 20
  recommend-limit: 10
```

业务实现提供六项 AI 能力；但完全无密钥启动存在 Spring AI 自动配置阻碍，需使用 [README](../README.md) 中的 Mock 启动命令：简历分析走规则评分、岗位匹配使用技能/经验/学历规则 + 本地 n-gram 向量语义、推荐批量计算、优化走规则化改写、面试走内置题库与规则评分，助手走招聘主题规则回答。

### 2.3 真实模式配置（接入 OpenAI 兼容大模型）

```yaml
ai:
  enabled: true
  mock: false
  base-url: "https://api.openai.com"      # 或任意 OpenAI 兼容网关地址，通常不手动追加 /v1
  api-key: "sk-..."                       # 真实密钥，请勿提交到仓库
  model: gpt-4o-mini                      # 对话模型
  embedding-model: text-embedding-3-small # 向量模型
  embedding-enabled: true                 # DeepSeek 等无兼容 Embedding 时可设为 false
```

配置说明：

- 密钥只通过 ai.api-key 配置读取，**接口与文档不回显明文**（/api/admin/ai/config 仅返回 hasApiKey 布尔值）。
- Spring AI 的 ChatClient 与 EmbeddingModel 由 application-dev.yml / application-prod.yml 按 ai.* 前缀映射（spring.ai.openai.api-key/base-url、chat.options.model、embedding.options.model）。
- `base-url` 通常填写根地址，不要让 Spring AI 再拼一次 `/v1`；对接的接口需兼容 OpenAI 的 chat 与 embeddings 协议。
- `AiProperties` 声明 temperature=0.4、max-tokens=2000、timeout-seconds=30，但后两项未传给调用客户端，不能保证 token 上限或 30 秒截止；profile 的 Chat options 当前固定 temperature=0.4；`embedding-enabled=false` 时语义匹配直接使用本地向量。
- Docker 部署时可通过环境变量覆盖：AI_ENABLED、AI_MOCK、AI_API_KEY、AI_BASE_URL、AI_MODEL、AI_EMBEDDING_MODEL、AI_EMBEDDING_ENABLED（见 docker-compose.yml 注释）。

### 2.4 模式探测与连通性测试

- `GET /api/common/health`（公开）返回：
  `{ "status": "UP"|"DEGRADED", "mysql": boolean, "redis": boolean, "ai": { "mode": "REAL"|"MOCK"|"DISABLED", "enabled": boolean, "mock": boolean, "hasApiKey": boolean } }`
- `GET /api/admin/ai/config`（ADMIN）返回 mode、enabled、mock、baseUrl、model、embeddingModel、embeddingEnabled、hasApiKey（脱敏）、recommendPoolSize、recommendLimit。
- `POST /api/admin/ai/test`（ADMIN，无 body）执行连通性测试：MOCK 模式返回 ok=true 提示无需外部模型；REAL 模式发起一次真实对话，返回 ok、message、reply（超过 50 字截断）与 latencyMs。

## 三、AI 模块代码设计

### 3.1 AiProperties（ai/config/AiProperties.java）

@ConfigurationProperties(prefix = "ai")，字段与 2.2 节 yml 一一对应；提供 realMode() 与 displayMode() 供全局判断模式。

### 3.2 LlmClient（ai/llm/LlmClient.java）

封装 Spring AI ChatClient：

- `chat(system, user)`：单轮对话返回文本；非 realMode 或调用失败时抛出 AI 业务异常（code 503，message 提示检查配置/网络）。
- `chatJson(system, user)`：在 chat 基础上要求模型“只输出 JSON”，并做清洗——剥离 Markdown 代码块围栏（含 json 语言标记），并裁剪到首个 { 与最后一个 } 之间，供 JsonUtils 反序列化。
- 简历解析/分析/优化、面试与助手使用 chatJson；匹配理由使用 chat 获取正文。调用或结构化解析失败时按服务的回退分支处理。

### 3.3 EmbeddingClient（ai/embedding/EmbeddingClient.java）

向量化客户端，用于语义相似度：

- 真实模式（realMode 且有 EmbeddingModel Bean）调用 Embedding 模型生成向量，失败自动回退本地向量。
- 本地确定性向量 localEmbed：文本小写化后按 2-gram 哈希映射到 128 维稀疏桶并归一化，无需网络、结果可复现。
- 提供静态 cosine() 余弦相似度，取值裁剪到 [0,1] 后 ×100 得到语义分。

### 3.4 AiServiceConfig（ai/config/AiServiceConfig.java）

按 realMode() 自动装配 ResumeAnalysisService / ResumeOptimizationService 的 Real 或 Mock 实现，业务代码无感知；JobMatchService / AiInterviewService / RecommendationService / ChatAssistantService 在方法内部按 realMode() 分支，并统一 try-catch 降级规则路径。

### 3.5 AI 智能助手子包（ai/chat）

| 类 | 职责 |
| --- | --- |
| ChatContext | 上下文数据载体（求职者/企业/管理员/当前岗位四类字段） |
| ChatContextProvider | 从各业务 Mapper 汇总上下文，单点查询失败只记 WARN |
| ChatPrompt | 真实模式的 system/user Prompt 拼装（含 10 条历史滑动窗口） |
| ChatMockEngine | 25 个主题的规则回答库 + 推荐追问补齐（`ChatMockEngineTest` 已覆盖） |
| ChatAssistantService | 编排问答、持久化会话与消息、欢迎语与对话记录（`ai/service/ChatAssistantService.java`） |

### 3.6 Prompt 设计说明

- LLM 使用中文 system 与场景化 user 上下文；解析/分析/优化、面试及助手要求结构化 JSON，匹配推荐理由要求自然语言正文。
- 简历分析 system：“资深招聘顾问……只输出 JSON：{overallScore, skillScore, experienceScore, educationScore, completenessScore, strengths[], weaknesses[], suggestions[], targetJobs[]}”。
- 简历优化 system：“对照目标岗位 JD 优化简历，只输出 JSON：{summary, items:[{field, original, optimized, suggestion, keywords[]}]}”。
- 面试出题 system：“技术面试官，生成题目，只输出 JSON：{questions:[{question, questionType, difficulty}]}”；逐题评分 system 要求 {score, feedback}；结束总评要求 {strengths, weaknesses, suggestions}。
- 岗位匹配推荐理由 system 明确“不要输出 JSON，直接输出正文”（自然语言理由）。
- 助手问答 system：“你是「智聘AI」招聘平台的智能助手……”要求只输出 `{reply, suggestions[]}`，并约束纯文本、400 字以内、结合用户资料（详见 9.4）。
- LLM 输出经 chatJson 清洗后由 Jackson 解析；任何解析失败/超时/网络异常都进入 catch 并降级为规则实现，保证接口 200 可用。

## 四、简历分析（Resume Analysis）

### 4.1 接口与流程

- `POST /api/ai/resume/analyze/{resumeId}` [USER]：对本人简历执行 AI 分析（非本人 403/404），成功即持久化并返回结果。
- `GET /api/ai/resume/analysis/{resumeId}` [USER]：读取最近一次分析结果（不触发重算）。
- 分析内容基于简历基本信息、技能、个人简介与全部经历文本（JobMatchService.buildResumeText 拼装上下文）。

真实模式：RealResumeAnalysisService 将简历文本交给 LLM（结构化 JSON：五维评分 + 三组数组 + 适配岗位），解析后落库；异常则降级 MockResumeAnalysisService（规则）。

### 4.2 返回结构 AiAnalysisVO

```json
{
  "id": 1, "resumeId": 1, "resumeName": "王小明",
  "overallScore": 88, "skillScore": 92, "experienceScore": 85,
  "educationScore": 80, "completenessScore": 95,
  "strengths": ["Java 基础扎实，熟练使用 Spring Boot 全家桶"],
  "weaknesses": ["缺少微服务与消息队列等中高级技能"],
  "suggestions": ["补充学习 Spring Cloud、Kafka 等微服务组件"],
  "targetJobs": ["Java后端开发", "全栈开发"],
  "source": "RULE", "createTime": "2026-09-09T10:00:00"
}
```

### 4.3 评分维度

| 字段 | 含义 | Mock 规则要点 |
| --- | --- | --- |
| overallScore | 综合评分 | skill×30% + experience×30% + education×20% + completeness×20% 后四舍五入 |
| skillScore | 技能评分 | min(96, 45 + 技能数×8 + 热门技能命中奖励 12)，热门技能：java/spring/mysql/redis/vue/python/docker |
| experienceScore | 经历评分 | 有工作/实习经历 84；项目≥2 个 80；项目≥1 个 72；否则 55；个人简介>100 字 +8（封顶 100） |
| educationScore | 学历评分 | 博士 96 / 硕士 92 / 本科 86 / 大专 74 / 其他 58 |
| completenessScore | 完整度 | 直接取简历 completionScore（10 项 × 10 分：姓名/电话/邮箱/学校/学历/专业/技能≥3/摘要>30 字/有经历/有附件） |

strengths / weaknesses / suggestions 由简历内容特征（技能栈、经历类型、摘要等）模板化生成；targetJobs 按技能关键词判定适配方向（Java/Spring→Java 开发、Vue→前端、Python→算法/数据分析、MySQL/Redis/Docker→后端运维等）。

### 4.4 持久化

结果写入 ai_resume_analysis（按 resume_id 先删后插，uk_resume_id），刷新/重启后 GET 仍可读到报告，适合答辩演示“数据可复盘”。

补充：`ai_resume_analysis` 表不保存 `source`。POST 分析接口会在实时响应中返回 `LLM` / `RULE`，GET 最近结果由数据库行组装，未设置该字段，因此通常为 `null`。

## 五、岗位匹配（Job Match）

### 5.1 接口

`POST /api/ai/match` [USER]，body `{ "jobId": 123, "resumeId": 9 }`（resumeId 可选且必须为本人简历）；岗位须为 ONLINE。未传 resumeId 时服务端取当前用户最近一份简历（latestResume），无简历返回 400“请先创建并完善简历，再进行 AI 匹配”。

### 5.2 综合评分公式

```
综合匹配度 = 语义匹配 × 50% + 技能匹配 × 25% + 经验匹配 × 15% + 学历匹配 × 10%
```

| 维度 | 权重 | 计算方式 |
| --- | --- | --- |
| 语义匹配 semanticScore | 50% | 简历全文 vs 岗位 JD 的 Embedding 向量余弦相似度 ×100 |
| 技能匹配 skillScore | 25% | 岗位技能按 weight 加权：命中技能权重和 / 总权重 ×100 |
| 经验匹配 experienceScore | 15% | 按岗位经验要求与简历 WORK/INTERNSHIP/PROJECT 数量打分 |
| 学历匹配 educationScore | 10% | 学历等级对照（大专1/本科2/硕士3/博士4），达标 100，差 1 档 80、差 2 档 60、其余 40；要求“不限”得 100 |

匹配结果裁剪在 0-100。matchedSkills 为简历已具备的岗位技能，missingSkills 为缺失技能（推荐补齐项）。

### 5.3 语义 Embedding 说明

- 简历侧文本：姓名/学历/学校/专业/技能/简介/全部经历（标题+时间+内容）拼接。
- 岗位侧文本：岗位名/类型/城市/描述/要求/技能标签拼接。
- 真实模式：Embedding 模型生成语义向量（维度取决于所选模型） → 余弦相似度；
- Mock/失败：localEmbed 本地 2-gram 哈希 128 维稀疏向量（归一化）→ 余弦相似度，确定性、零网络依赖。

### 5.4 推荐理由

匹配后按参数决定是否生成推荐理由：真实模式调用 LLM 生成 80-150 字个性化理由（结合命中/缺失技能与语义分），失败回退模板；Mock 模式直接由模板拼接（如“你的技术栈与岗位要求高度匹配（如 Java、Spring Boot）。建议补充 Kafka、分布式 相关经验……”）。

### 5.5 返回示例 MatchResultVO

```json
{
  "jobId": 1, "jobName": "Java开发工程师", "companyName": "上海星云网络科技有限公司", "companyLogo": null,
  "matchScore": 92, "skillScore": 95, "experienceScore": 90,
  "educationScore": 80, "semanticScore": 93,
  "matchedSkills": ["Java", "Spring Boot", "MySQL", "Redis", "MyBatis"],
  "missingSkills": ["Docker"],
  "reason": "你的 Java 与 Spring Boot 技术栈与岗位要求高度匹配，实习经历中的性能优化实践是加分项。",
  "source": "RULE"
}
```

> 匹配 source 根据实际路径返回 LLM/RULE/FALLBACK；semanticSource 分别为 EMBEDDING/LOCAL/FALLBACK，reasonSource 为 LLM/RULE/FALLBACK，executionNote 提供执行说明。单次匹配和投递不改写推荐批次。任一向量调用失败时两个文本统一使用本地向量，避免混用向量空间。
> 该 `source` 仅存在于匹配计算的实时返回中；`ai_recommendation` 不保存 source，推荐列表从数据库读取时也不会返回该字段。

## 六、岗位推荐（Recommendations）

### 6.1 接口

- `GET /api/ai/recommendations` [USER]：返回推荐岗位列表（首次自动计算；结果新鲜时直接读缓存）。
- `POST /api/ai/recommendations/refresh` [USER]：强制重算。

### 6.2 候选池与排序

1. 取当前用户最近一份简历；无简历返回空列表。
2. 取全部 ONLINE 岗位及其技能；简历技能与岗位技能存在任意命中即进入候选池（命中数量受 recommend-pool-size 限制，默认 20）。
3. 若无任何命中岗位，则退化为取在线岗位前 pool-size 个作为候选。
4. 对候选逐个执行 JobMatchService.compute（同岗位匹配的四维公式），按 matchScore 降序取前 recommend-limit（默认 10）条。

### 6.3 缓存与持久化

- 计算结果**持久化** ai_recommendation（先清空该用户旧推荐再批量插入 Top N，uk_user_job 防重复）。
- 新鲜度判断：批次中每条 create_time 都必须在 6 小时以内且晚于最新简历 update_time；简历创建、更新、删除、上传使该用户推荐失效，企业/管理员岗位发布、修改、上下架或删除使推荐批次失效。GET 过滤已删除/下架岗位，并使用按 user_id 查询的最新简历重建技能命中；超时或手动 refresh 重算。
- RecommendItemVO 字段：jobId/jobName/jobType/city/salaryMin/salaryMax/education/experience/companyId/companyName/companyLogo/matchScore/skillScore/experienceScore/educationScore/semanticScore/matchedSkills/missingSkills/reason。

预置数据中 user（王小明）已带 4 条推荐记录（92/86/88/90 等），登录即可直接演示；点击“刷新推荐”可观察重算链路。

## 七、简历优化（Resume Optimization）

优化约束：只改善输入事实的表达，禁止编造技能、经历或业绩数字。规则优化不添加未使用的 JD 技术，也不生成“提升 30%”等虚构数据；缺失技能仅作为学习建议。用户核对原文与建议后自行采用。

### 7.1 接口

`POST /api/ai/resume/optimize` [USER]，body（均必填）：`{ "resumeId": 1, "jobId": 1 }`。服务端按该岗位 JD 定向优化简历，返回逐条对比结果（不落库，前端展示原文/优化后供用户确认回填）。

### 7.2 返回结构 OptimizeResultVO

```json
{
  "resumeId": 1, "jobId": 1, "jobName": "Java开发工程师",
  "summary": "针对【Java开发工程师】岗位要求，重点优化了个人简介、项目经历与技能关键词。建议补充 Spring Cloud、Kafka 相关技能与案例。",
  "items": [
    {
      "field": "个人简介",
      "original": "热爱技术的Java后端开发工程师，熟悉企业级应用开发全流程……",
      "optimized": "华东理工大学计算机科学与技术专业背景，熟悉 Java、Spring Boot、MySQL、Redis……",
      "suggestion": "将个人简介与目标岗位 JD 对齐，突出 2-3 项最相关能力",
      "keywords": ["Spring Cloud", "Kafka"]
    },
    {
      "field": "项目/工作经历",
      "original": "参与企业级OA系统研发……",
      "optimized": "……（AI/规则按 JD 重写，突出职责、技术栈与量化成果）",
      "suggestion": "按 STAR 法则补充背景、行动与量化结果",
      "keywords": []
    }
  ]
}
```

### 7.3 两种实现

- Real：RealResumeOptimizationService 把简历全文 + 岗位 JD/技能交给 LLM，要求 JSON 输出 summary 与 items（每条含 field/original/optimized/suggestion/keywords），结果供用户对照核实，前端不会自动覆盖原简历。
- Mock：MockResumeOptimizationService 规则化改写——个人简介与 JD 对齐重写；项目/工作经历文本润色并突出技能；第三项“技能关键词”把岗位要求而简历缺失的技能作为建议补充关键词输出。Mock 与 Real 输出同构，前端渲染逻辑完全一致。

## 八、AI 模拟面试（Mock Interview）

### 8.1 接口（均 [USER]，除 start/list 外校验“本人面试”）

| 方法/路径 | 说明 |
| --- | --- |
| POST /api/ai/interview/start | 开始面试并生成题目 |
| GET /api/ai/interview/list | 我的面试历史（InterviewVO[]） |
| GET /api/ai/interview/{id} | 面试详情（含题目与作答状态） |
| POST /api/ai/interview/{id}/answer | 逐题作答 + AI 评分点评 |
| POST /api/ai/interview/{id}/finish | 结束面试并生成报告 |
| GET /api/ai/interview/{id}/report | 获取面试报告 |

启动参数（InterviewStartRequest）：jobId（可选，目标岗位；缺省按综合技术方向出题）、difficulty（必填：简单/中等/困难）、questionCount（可选 3~10，默认 5）、title（可选自定义标题）。

### 8.2 出题

- Real：LLM 生成 `{questions:[{question, questionType, difficulty}]}`，questionType 建议取自 Java基础/Spring/MySQL/Redis/项目经验/场景题/算法；失败回退题库。
- Mock：内置题库按难度过滤后以时间种子随机打乱抽取（题库不足时全库随机），题目类型覆盖 Java基础/Spring/MySQL/Redis/项目经验/场景题等。
- 题目落库 ai_interview_question（含 sort 排序）；场次状态 ONGOING。

### 8.3 逐题作答与评分

- `POST /{id}/answer` body `{questionId, answer}`，answer 长度 5~4000；已结束（COMPLETED）的面试不可再作答。
- Real：LLM 评分，要求 JSON {score:0-100 整数, feedback:中文点评}；失败回退规则。
- Mock 规则评分：`score = min(100, 40 + min(30, 回答长度/10) + 命中技术关键词数×4)`（关键词如 索引/事务/缓存/Redis/MySQL/Spring/JVM/线程/锁/接口/数据库/分页/幂等/MQ/Docker/CI/监控/日志），并按分数档生成对应点评文案。
- 返回 InterviewQuestionVO（question/answer/score/feedback 已回填）。

### 8.4 结束与报告

- finish 要求至少作答一道题（否则 400）；totalScore = 已作答题分数平均（四舍五入）。
- dimensionScores：按题目类型分组取平均（如 Java基础/Spring/MySQL/项目经验 各得一分），作为雷达/条形图数据。
- strengths/weaknesses：按维度分生成（≥80 记为优势、<70 记为不足，各取最多 3 条，不足则补默认文案）；suggestions 按总分档生成复习建议。
- Real 模式额外让 LLM 依据完整问答记录生成总评三组文案（失败保留规则文案）。
- 报告 JSON 整体写入 ai_interview.report，场次置 COMPLETED，GET /{id}/report 随时可读。

## 九、AI 智能助手（智能问答 / 推荐追问 / 对话记录）

### 9.1 定位

对应软件构成图《用户用例图》中的「AI智能助手」（含「智能问答」「查看推荐追问」），以及用户结构图中的「AI智能助手 → 在线问答 / 对话记录 / 快捷追问」子节点。
入口是**页面右下角的悬浮气泡**，三种角色门户（求职者 / 企业 / 管理员）与登录页之外的公开页均可见；未登录访客也可直接问答，登录后对话自动落库。

### 9.2 接口

| 方法/路径 | 权限 | 说明 |
| --- | --- | --- |
| GET /api/ai/chat/greeting | public | 欢迎语 + 3 条快捷提问 + 当前 AI 模式 |
| POST /api/ai/chat/ask | public | 提问 → 回答 + 3 条推荐追问 |
| GET /api/ai/chat/history | public | 最近一次对话记录（未登录返回空） |
| GET /api/ai/chat/sessions | auth | 我的历史会话列表（最多 20 条） |
| DELETE /api/ai/chat/history | auth | 清空对话记录 |

请求体 `ChatAskRequest`：`{content(1~500 字), sessionId?, contextType?, contextId?}`；
`contextType=JOB` 时携带岗位详情页上下文（前端在岗位详情页自动带上当前岗位 id）。

### 9.3 数据感知上下文（ChatContextProvider）

回答不是泛泛而谈：服务端在每次提问时收集当前用户的业务数据，注入 Prompt 与规则引擎。

| 角色 | 注入内容 |
| --- | --- |
| USER | 最近一份简历（姓名/学历/专业/学校/技能/简介/完整度/经历）、投递数、面试中数量、Top5 推荐岗位与匹配度 |
| COMPANY | 企业名称、在招岗位数（含在线）、待处理投递数 |
| ADMIN | 平台注册求职者 / 入驻企业 / 在线岗位 / 待处理举报数 |
| 岗位详情页 | 岗位名、公司、城市、薪资、经验学历要求、要求技能、**已命中 / 缺失技能对比** |

例：求职者问「我缺哪些技能？」时，若正处于某岗位详情页，助手会直接列出该岗位要求的命中与缺失技能；问「我能匹配哪些岗位？」会引用 `ai_recommendation` 中的真实岗位名与匹配度。

### 9.4 真实模式 Prompt（ChatPrompt）

- system：“你是「智聘AI」招聘平台的智能助手……”并约定 5 条规则——仅答招聘/求职/简历/面试/职业/平台使用话题、中文口语化结论先行、**纯文本不用 Markdown**、400 字以内、结合用户资料不编造，最后要求只输出 JSON：`{reply, suggestions:[3 条 ≤20 字追问]}`。
- user：`【当前用户资料】`（上面 9.3 的数据）→ `【用户当前正在浏览的岗位】`（有则拼）→ `【近期对话】`（最近 10 条滑动窗口）→ `【用户本次提问】`。
- 输出经 `chatJson` 清洗 + Jackson 解析，取 `reply` 与 `suggestions`；解析失败/超时/网络异常一律降级规则引擎，通常回退规则路径返回业务结果；数据库、权限、输入和基础设施故障仍可能造成失败，不能保证接口恒成功。

### 9.5 Mock 规则引擎（ChatMockEngine）

- 主题库按角色装配：**求职者 19 个主题**（平台介绍、岗位匹配算法、岗位推荐、简历优化、简历分析五维、模拟面试、自我介绍、项目讲解、反问环节、沟通跟进、投递策略、谈薪、流程认知、职业发展、技能补强、实习校招、企业选择、Offer 对比、举报与我的数据），另加**企业 3 个**（候选人筛选、岗位发布、招聘漏斗）与**管理员 3 个**（平台数据、举报处理、AI 配置）。
- 匹配策略：统计提问命中的关键词个数，取命中最多者；全部未命中则走兜底回答（仍给出 3 条推荐追问）。
- 每个主题的回答都是「结论 + 分点 + 结合用户真实数据的个性化尾注」，并自带 3 条上下文相关的推荐追问。
- `completeSuggestions` 对追问去重并补齐到 3 条，保证前端「猜你想问」区域始终有内容。
- 已补充单元测试 `ChatMockEngineTest`（8 个用例，纯内存执行，不依赖 Spring 容器与数据库），覆盖关键词命中、数据注入、企业/管理员主题、兜底与追问去重。

### 9.6 对话记录与持久化

- `ai_chat_session`：一次会话一行，`title` 取首条提问前 30 字，`message_count` 随问答累加；
- `ai_chat_message`：USER / ASSISTANT 两类消息统一存放，助手消息额外保存 `suggestions`(JSON) 与 `source`(LLM/RULE)；
- 打开面板时前端调 `/history` 自动恢复最近一次会话（含推荐追问）；点面板「+」开启新对话（前端置空 sessionId，后端下一条提问即新建会话）；
- 未登录：`persisted=false`、`sessionId=null`，不写任何记录；跨用户传入他人 sessionId 会被忽略并新建自己的会话。

### 9.7 前端组件（AiChatWidget.vue）

- 挂在 `App.vue` 上（全局单例，位于 `<router-view>` 之外），`position: fixed; right/bottom: 24px`，仅 `/login`、`/register` 隐藏；
- 悬浮气泡带呼吸动效与 `AI` 角标；面板 390×620，含渐变头部（显示当前模式 REAL/MOCK/DISABLED 与会话状态）、新对话/清空/收起三个工具按钮、欢迎语、快捷提问、对话气泡、思考中动效、回答来源标注（AI 模型回答 / 规则引擎回答）、「猜你想问」追问区、输入框（Enter 发送、Shift+Enter 换行）；
- 文本渲染为轻量实现：仅支持 `**加粗**` 与换行，先做 HTML 转义再渲染，不引入 Markdown 依赖；未进行独立安全渗透验收；
- 未登录时输入区显示「登录保存记录」引导，可跳转登录页并回跳当前页面。

## 十、Mock 策略总结（用于答辩说明）

1. **规则可解释**：简历分析/优化、Embedding 本地 2-gram 向量与助手规则主题可按代码解释；面试题库使用当前时间作为随机种子，同一输入不保证相同题目，实时业务资料变化也会影响结果。
2. **零外部依赖**：不调用任何外部模型、不需要 API Key、不依赖网络，纯本地即可跑通六大功能，规避答辩现场网络风险。
3. **与真实模式同构**：Mock 与 Real 返回相同的 VO 结构与字段语义，实时响应中的 `source` 分别标识 RULE / LLM；前端一套代码适配两种模式，切换模式仅改配置、不动代码。
4. **数据真实落库**：分析、推荐、面试场次/题目/报告、助手会话与消息均写 MySQL，答辩可现场开库核对，展示“AI 结果可持久化”。
5. **自动降级**：即使真实模式下 LLM/Embedding 调用失败（超时、网络、额度等），服务捕获异常后回退规则路径继续返回结果，尽量维持业务返回；不涵盖数据库、鉴权、输入及基础设施异常。

说明：`source` 只保证在实时计算响应中区分 LLM / RULE；从数据库读取分析报告时不会恢复。简历优化不落库，属于即时辅助结果。

降级矩阵：

| 功能 | 真实模式 | 降级行为 |
| --- | --- | --- |
| 简历分析 | LLM 五维 JSON | 回退 MockResumeAnalysisService 规则分析（source=RULE） |
| 简历优化 | LLM 对照 JD JSON | 回退 MockResumeOptimizationService 规则改写 |
| 匹配推荐理由 | LLM 生成自然语言理由 | 回退模板拼接理由；评分本身始终可算 |
| 语义向量 | Embedding 模型 | 回退本地 n-gram 128 维向量，余弦相似度不变式 |
| 面试出题 | LLM 出题 | 回退内置题库按难度抽取 |
| 逐题评分/总评 | LLM 评分 | 回退规则评分 / 规则总评文案 |
| 助手问答 | LLM 多轮 JSON 回答 | 回退 25 个主题规则库（source=RULE），追问仍补齐 3 条 |

## 十一、真实 LLM 接入 Checklist

| 步骤 | 操作 | 验证 |
| --- | --- | --- |
| 1 | 在 application.yml（或 dev/prod profile）开启 `ai.enabled: true`、`ai.mock: false` | - |
| 2 | 配置 `ai.base-url` 为 OpenAI 兼容根地址（默认 https://api.openai.com，通常不手动追加 /v1） | - |
| 3 | 配置 `ai.api-key`（真实密钥；切勿提交仓库/写进文档） | - |
| 4 | 配置对话模型 `ai.model`、向量模型 `ai.embedding-model`，并按供应商能力设置 `ai.embedding-enabled` | 模型需支持对应协议；无 Embedding 时使用本地向量 |
| 5 | 重启后端 | 启动日志无异常 |
| 6 | GET /api/common/health | ai.mode=REAL、mysql=true |
| 7 | admin 登录后 GET /api/admin/ai/config | baseUrl/model/embeddingEnabled 正确、hasApiKey=true |
| 8 | POST /api/admin/ai/test | ok=true、返回模型回复与 latencyMs |
| 9 | 分别试跑：简历分析、岗位匹配、推荐 refresh、简历优化、模拟面试出题/评分/报告、右下角助手问答 | 每条功能返回正常；有失败可观察后端 WARN 日志确认已降级 |
| 10 | 关闭 ai.enabled 或清空 api-key 即可回到 MOCK/DISABLED | health 中 mode 随之变化 |

注意事项：

- base-url 需为 OpenAI 兼容的 /chat/completions、/embeddings 协议端点（Spring AI OpenAI Starter 装配），自建网关需兼容其格式。
- `base-url` 传服务根地址即可，Spring AI OpenAI Starter 会按约定拼接 API 路径；不要把 `/v1` 写成重复前缀。
- 后端对模型输出一律做 JSON 清洗与容错解析，业务层不信任模型格式；评分字段越界（如 >100）由规则路径兜底或二次裁剪。
- Embedding 维度无需配置：代码只做向量归一化与余弦点积，兼容不同维度模型。
- 日志级别建议保持 org.springframework.ai: warn，避免真实调用时刷屏。
- 真实模式的回退逻辑尽量维持业务闭环，但外部请求可能阻塞或超过前端 20 秒超时；真实模型与网络故障场景未在本次联网验收。

## 十二、日志与审计（AI 相关）

AI 操作使用 `@OpLog` 注解，例如模块“AI简历分析”动作“分析简历”、模块“AI模拟面试”动作“开始面试”、模块“AI 智能助手”动作“智能问答/清空对话”。但当前 `OperationLogAspect` 统一调用 `saveOperateLog`，所以这些记录实际写入 `sys_log.type=OPERATE`；`saveAiLog`（type=AI）尚未接入业务调用。初始化数据中另有 AI 类型的示例日志，便于后台日志页展示和过滤。

## 十三、常见问题

- 为什么 Mock 不需要真实 Key？——业务走规则分支；当前 Spring AI 自动配置仍要求非空框架连接值，完全空值启动失败。README 的命令只为 spring.ai.openai.api-key 提供非真实占位值，不开启真实调用。
- 如何确认当前模式？——GET /api/common/health 或后台 AI 配置页（mode: REAL/MOCK/DISABLED）；助手面板头部也会显示当前 mode。
- 接真实模型后结果反而慢？——ai.timeout-seconds 尚未接入客户端，不能保证 30 秒超时。推荐评分当前在 for 循环中顺序计算，且 compute(..., false) 不请求 LLM 理由；真实 Embedding 仍可能影响耗时。
- 模型返回非 JSON？——chatJson 自动剥离代码块并截取 JSON 区间；解析仍失败则降级规则，不影响页面。
- 密钥会泄露吗？——/api/admin/ai/config 只返回 hasApiKey 布尔，永不含明文；请勿把真实 key 提交到仓库或文档。
- 右下角助手在哪些页面出现？——除登录/注册页外的所有页面（三种角色门户通用）；未登录可直接问答，只是不保存对话记录。
- 助手的对话记录存在哪？——`ai_chat_session`（会话）+ `ai_chat_message`（消息，含推荐追问与来源），点面板「清空」按钮会删除当前用户全部记录。
